## 2. 量化方案

### 2.1 量化策略示意图

```
┌─────────────────────────────────────────────────────────────┐
│                    量化策略 (4-bit FP4)                      │
│                                                             │
│  ┌────────────────────┐    ┌────────────────────────────┐   │
│  │   LLM 主干 (量化)   │    │   TTS 模块 (不量化)         │   │
│  │                    │    │                            │   │
│  │  ┌──────────────┐  │    │  ┌──────────────────────┐  │   │
│  │  │ 28层 Transformer│  │    │  │ emb_text    (FP32)  │  │   │
│  │  │              │  │    │  │ emb_code    (FP32)  │  │   │
│  │  │ Attention    │  │    │  │ head_code   (FP32)  │  │   │
│  │  │   Q/K/V/O    │  │    │  │ projector   (FP32)  │  │   │
│  │  │     ↓ 4-bit  │  │    │  │ audio_tokenizer(FP32)│  │   │
│  │  │   FFN       │  │    │  │ Token2wav   (FP32)  │  │   │
│  │  │   Gate/Up/Down│  │    │  └──────────────────────┘  │   │
│  │  │     ↓ 4-bit  │  │    │                            │   │
│  │  │ Embedding    │  │    │  保持全精度 (FP32/FP16)       │   │
│  │  │   (部分量化)  │  │    │  原因: weight_norm 不兼容     │   │
│  │  └──────────────┘  │    │         量化后 CB 属性         │   │
│  │                    │    │                            │   │
│  │  量化类型: FP4      │    │  显存占用: ~2 GB             │   │
│  │  计算精度: FP16     │    └────────────────────────────┘   │
│  │  双重量化: 关闭     │                                      │
│  │                    │                                      │
│  │  显存占用: ~8 GB    │                                      │
│  └────────────────────┘                                      │
│                                                             │
│  总显存: 8 + 2 + 2.8(KV/激活) = ~12.8 GB / 24 GB            │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 量化配置详解

```python
BitsAndBytesConfig(
    # 量化开关
    load_in_4bit=True,                      # 启用 4-bit 量化

    # 计算精度
    bnb_4bit_compute_dtype=torch.float16,   # 前向计算用 FP16

    # 量化类型
    bnb_4bit_quant_type="fp4",              # FP4 (非 NF4)
    # FP4: 范围 [-6, 6]，均匀分布
    # NF4: 范围 [-1, 1]，正态分布 (更适合权重)

    # 双重量化
    bnb_4bit_use_double_quant=False,        # 关闭双重量化
    # 双重量化会进一步压缩量化常数，但增加计算开销

    # 跳过量化的模块
    llm_int8_skip_modules=[
        "tts",              # TTS 主模块
        "head_code",        # 语音码本头 (weight_norm 包装)
        "emb_code",         # 语音码本嵌入
        "emb_text",         # 文本嵌入
        "projector",        # 模态投影层
        "audio_tokenizer",  # 音频分词器
        "Token2wav"         # Token 转波形模块
    ],
)
```

### 2.3 量化精度对比

| 精度 | 参数量等效 | 显存 (LLM) | 信息损失 | 语音质量 |
|------|-----------|-----------|---------|---------|
| **BF16** (原始) | 9B × 16-bit | ~18 GB | 0% | 完美 |
| **8-bit** | 9B × 8-bit | ~9 GB | 50% | 乱码 |
| **4-bit NF4** | 9B × 4-bit | ~4.5 GB | 75% | "嗯" |
| **4-bit FP4** | 9B × 4-bit | ~4.5 GB | 75% | "能听到" |

## 4. 网络访问问题

### 问题：浏览器拒绝麦克风访问

通过 `http://100.94.242.79:8032` 访问时，浏览器报错：
> "请通过 localhost 或 HTTPS 打开页面，以使用麦克风和摄像头。"

**原因**：浏览器的安全策略——麦克风/摄像头只允许在 `localhost` 或 `HTTPS` 下使用。Tailscale 的 100.x.x.x 地址虽然在同一网络，但浏览器不将其视为安全上下文。

**解决方案**：在笔记本上开 SSH 隧道：
```bash
ssh -N -L 8032:127.0.0.1:8032 wangwei@100.94.242.79
```
然后笔记本浏览器打开 `http://localhost:8032`。

**配置**：`config.json` 中 `web.host` 设为 `0.0.0.0`（允许外部访问）。

RTX 3090 共 24GB VRAM，但 9B 模型 + TTS 需要 ~22GB，加上系统占用后超出限制。

## 6. 所有尝试过的方案

### 尝试 1：BF16 全精度 + `expandable_segments`

**方案**：以 `torch.bfloat16` 全精度加载模型，设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 减少显存碎片。

**结果**：❌ CUDA Out of Memory

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 1.95 GiB.
GPU 0 has 23.56 GiB total, 1.91 GiB free.
This process has 21.30 GiB memory in use.
```

- 模型占用：21.3 GB
- TTS 需要：~2 GB
- 可用：1.91 GB ❌

**结论**：显存不够，`expandable_segments` 只解决碎片问题，不减少总量。

---

### 尝试 2：8-bit 量化（LLM + TTS 全部量化）

**方案**：通过 `sitecustomize.py` 钩子注入 `BitsAndBytesConfig(load_in_8bit=True)`。

**结果**：❌ TTS 推理崩溃

```
AttributeError: 'Parameter' object has no attribute 'CB'
```

- 模型显存：13.7 GB ✅
- 但 TTS 的 `head_code` 层（`weight_norm(nn.Linear)`）被 8-bit 量化后无法工作
- `weight_norm` 的参数结构与 bitsandbytes 的 `CB` 属性不兼容

---

### 尝试 3：8-bit 量化 + 跳过 TTS 模块

**方案**：在 `BitsAndBytesConfig` 中添加 `llm_int8_skip_modules=["tts", "head_code", "emb_code", "emb_text", "projector", "audio_tokenizer", "Token2wav"]`，让 TTS 保持全精度。

**结果**：⚠️ 模型加载成功，但无语音输出

- 模型显存：13.8 GB ✅
- TTS 模块全精度加载成功 ✅
- 模型收到音频输入 ✅
- 但**不生成任何语音 token**（output 端点持续 408 Timeout）
- 8-bit 量化破坏了 LLM 的语音 token 生成能力

**结论**：8-bit 量化对语音生成损伤太大。

---

### 尝试 4：4-bit NF4 量化 + 跳过 TTS

**方案**：改用 `load_in_4bit=True`，`bnb_4bit_quant_type="nf4"`，`bnb_4bit_use_double_quant=True`。

**结果**：⚠️ 能出语音，但只说一句

- 模型显存：10.4 GB ✅
- 能生成 "嗯" 等简单回复 ✅
- 但之后不再生成语音 ❌
- 日志：`audio_past_key_values length 1502 exceed 1500, reset`（反复出现）

**结论**：4-bit NF4 量化仍不足以维持持续对话能力。

---

### 尝试 5（当前）：4-bit FP4 量化 + 跳过 TTS

**方案**：改用 `bnb_4bit_quant_type="fp4"`，`bnb_4bit_compute_dtype=torch.float16`，`bnb_4bit_use_double_quant=False`。

**结果**：⚠️ 略有改善，但仍不完整

- 模型显存：10.7 GB ✅
- 能生成 "能听到" 等短语 ✅
- 模型回复了 2 次后停止 ❌
- 之后 `audio_past_key_values` 反复 exceed 1500 并 reset
- 模型不再响应新的语音输入

**日志记录**：
```
22:49:48  用户说话（151个语音token）
22:49:52  模型回复 "能听到"（5个语音token）  ← 成功！
22:49:54  模型补充一句（4个token）           ← 成功！
22:50:18  audio_past_key_values exceed 1500, reset
22:50:47  audio_past_key_values exceed 1500, reset  ← 不再回复
22:51:16  audio_past_key_values exceed 1500, reset
...（每30秒重复一次，模型无响应）
```

**结论**：4-bit FP4 略好于 NF4（能出完整短语），但持续对话能力仍然不足。

## 7. 总结

### 量化方案对比

| 方案 | 显存 | 语音效果 | 持续对话 | 评价 |
|------|------|----------|----------|------|
| **BF16 全精度** | 21.3 GB | 完美 | 完美 | ❌ OOM |
| **8-bit 全量化** | 13.7 GB | — | — | ❌ TTS 崩溃 |
| **8-bit + skip TTS** | 13.8 GB | 无输出 | — | ❌ 语音token损坏 |
| **4-bit NF4** | 10.4 GB | "嗯" | ❌ 1句后停止 | ⚠️ 勉强可用 |
| **4-bit FP4** | 10.7 GB | "能听到" | ❌ 2句后停止 | ⚠️ 略有改善 |

### 根本原因分析

**瓶颈不在 TTS，而在 LLM 主干。**

从日志可以清楚看到：

```
22:49:52  model speak ids=(151706, 26232, 104188, 151718, 151684)  ← LLM 生成了语音 token
22:49:54  model speak ids=(151706, 151717, 151718, 151684)          ← 又生成了一句
22:50:18  audio_past_key_values length 1502 exceed 1500, reset      ← KV cache 超长被重置
22:50:47  audio_past_key_values length 1502 exceed 1500, reset      ← 又是 reset
...（之后再没有 "model speak" 的日志）
```

**TTS 模块一直正常工作**（全精度，没量化），问题出在 LLM 不再生成语音 token：

1. LLM 前两次成功生成了语音 token → TTS 正常接收并播放了
2. 音频上下文超过 1500 token → KV cache 被强制 reset
3. reset 后 LLM 丢失了对话历史
4. **4-bit 量化的模型恢复能力差**——无法从 reset 中恢复语音生成能力
5. 模型陷入沉默，不再输出任何语音 token

**为什么 4-bit 模型恢复不了？**

- KV cache reset 后，模型需要重新理解对话状态
- 全精度模型（BF16）能快速恢复，因为它有足够的精度来推断上下文
- 4-bit 模型权重被压缩了 75%（18GB → 4.5GB），信息损失太大
- 量化后的模型"忘了"该继续生成语音，陷入沉默

**结论**：这不是 TTS 的 bug，而是 LLM 被量化后变笨了，在 KV cache reset 后无法恢复语音生成能力。

```
┌─────────────────────────────────────────────────────────────┐
│                 问题根因示意图                                │
│                                                             │
│  用户说话 → LLM(4-bit) → 语音 token → TTS(全精度) → 音频     │
│                                                             │
│  第 1 轮：                                                   │
│  ┌──────────┐    ┌─────────────┐    ┌──────────┐            │
│  │ 用户说话  │ → │ LLM 生成 token│ → │ TTS 播放  │  ✅ 成功   │
│  └──────────┘    └─────────────┘    └──────────┘            │
│                                                             │
│  第 2 轮：                                                   │
│  ┌──────────┐    ┌─────────────┐    ┌──────────┐            │
│  │ 用户说话  │ → │ LLM 生成 token│ → │ TTS 播放  │  ✅ 成功   │
│  └──────────┘    └─────────────┘    └──────────┘            │
│                                                             │
│  第 3 轮：                                                   │
│  ┌──────────┐    ┌─────────────┐    ┌──────────┐            │
│  │ 用户说话  │ → │ LLM 不生成！  │ → │ TTS 等待  │  ❌ 沉默   │
│  └──────────┘    └─────────────┘    └──────────┘            │
│                                                             │
│  原因：KV cache reset 后，4-bit LLM 无法恢复语音生成能力      │
└─────────────────────────────────────────────────────────────┘
```

---

**RTX 3090 (24GB) 跑不了这个 9B 全双工语音模型。**

- BF16 全精度需要 ~22GB 显存（模型 ~18GB + TTS ~2GB + 系统 ~2GB）
- RTX 3090 可用显存约 23.5GB（扣除 Xorg 等系统占用）
- 量化到 4-bit 能解决显存问题（10.7GB），但 LLM 推理能力严重下降
- 4-bit 将 9B 参数压缩到 ~4.5GB（原始 18GB），信息损失 75%
- 语音生成对权重精度非常敏感——模型能生成 1-2 句简单回复，但无法维持持续对话

## 10. 最终解决方案：Context Sliding Window（2026-11-15）

### 问题

模型输出"好的，我明白了"后停止响应，需要频繁重连。

### 根本原因分析

1. **硬件限制**：RTX 3090 (24GB) 无法以全精度运行 9B 模型
2. **8-bit 量化影响**：量化后模型在 KV cache reset 后恢复能力差
3. **硬重置问题**：`audio_past_key_values` 超过 1500 token 时执行 `self.audio_past_key_values = None`，对话上下文完全丢失

### 解决方案

启用 **context sliding window**（上下文滑动窗口）：

```python
# sitecustomize.py 钩子
module.MiniCPMODuplex._default_duplex_params["sliding_window_mode"] = "context"
module.MiniCPMODuplex._default_duplex_params["context_previous_max_tokens"] = 500
module.MiniCPMODuplex._default_duplex_params["context_max_units"] = 24
```

**工作原理**：
- 模型不再硬重置 KV cache（`self.audio_past_key_values = None`）
- 而是滑动窗口：保留最近 500 token 的上下文
- 对话历史被平滑截断，而非突然丢失
- 模型能持续保持对话连贯性
